# Make access the required authorization source

All plugins with protected operations depend at runtime on `memebot-access`, which is the sole source of administrator and management-location authorization. Authorization uses one global administrator set and one global management-group set shared by every protected plugin, including plugins added later; there are no plugin-specific overrides. A Koishi user with authority 4 or higher is always an administrator, providing a fixed bootstrap and recovery path. Access owns no business-notification routing, so each plugin continues to configure its own notification recipients.

Console management surfaces use Koishi's Console authentication integration when Koishi Auth/Login is installed. In that mode, protected plugin pages are not offered as navigable sidebar entries before authentication succeeds, and every corresponding backend listener independently rejects unauthenticated access. Any successfully authenticated Console account receives complete access to every plugin management interface, including access administration, without an additional authority-level check. When Koishi Auth/Login is absent, Console management surfaces remain available without authentication; installing the login plugin is therefore the deployment's explicit security boundary rather than a runtime or package dependency. Chat-based management remains governed separately by the global administrator and management-group rules. This is a deliberate exception to the repository rule that one `memebot-*` plugin must not require another: optional integration with local fallback would preserve two competing authorization models and allow their behavior to diverge again.

The Koishi database is the runtime source of truth for administrators and management groups. Plugin configuration may seed both sets only when authorization storage is initially empty and must never overwrite later Console changes. The access plugin integrates with database and Console through the ordinary Koishi plugin service-injection and Console authority mechanisms; it does not take a package-level dependency on Koishi's login plugin.

Authorization records are deliberately QQ-specific: administrators are stored by QQ user number and management groups by QQ group number. Cross-platform identity modeling is outside the product boundary.

For chat-based management, administrator-only reads require identity but are not restricted by location. Private conversations are valid locations for state changes by an administrator. State changes in group conversations require the group to be present in the global management-group set; an empty set denies state changes in every group. Console operations are not subject to management-location checks.
